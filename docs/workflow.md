# レポートを作るまでの手順

相談を始めてから、同行者に見せるレポート（提案の資料）ができるまでの流れです。段階ごとに、誰が何をして、何を保存するかを書きます。

- なぜそうするかは [design.md](design.md) にあります（段階の深さは §3、データの持ち方は §8、レポートの考え方は §17、試運転でわかったことは §18・§19）。
- 相談役と調査役への細かい指示は、定義のファイルが正です（`plugins/travel-agent/agents/*.md`、`plugins/travel-agent/skills/report/SKILL.md`）。ここには、流れと、人が確かめるところだけを書きます。
- データの場所と消し方は [README](../README.md) の「保存するデータと、消し方」にあります。下の `trips/<旅行ID>/` は、その場所の下です。

## 1. 全体の流れ

| 段階 | 相談役（concierge）がすること | 呼ぶ調査役 | ユーザーが決めること | 保存するもの |
|---|---|---|---|---|
| 相談 | 日程、人数、出発地、予算をまとめて聞く。予算は、固さ（上限／少しなら可／目安）、含めるもの、現地で使う追加の費用（昼食、現地の交通、入場料など。土産は入れない）、余りを残したいかも聞く。あいまいな言葉の意味を確かめる。数字で決めた条件と、例外を書きとめる | なし | 条件。予算の単位。食事の第一希望と、代わりの条件 | `conditions.json`（条件、仮置き、好みの定義、`rules`、`exceptions`）、`log.md` |
| 広く見る | 場所の候補を出し、交通を調べ、数字の条件に合わない場所を外す。宿を性格別に8〜12軒並べる | access（場所ごと）、scout（切り口ごと、夜ごと） | 残す場所と、残す宿 | `access.json`、`candidates/<宿ID>.json`（1軒1ファイル）、レポート `wide` |
| 比べる | 残った3〜5軒を、同じ深さで調べる。夜ごとの料金、税、口コミ、駅から宿までをそろえる | inspector（宿ごと） | さらに残す宿 | `candidates/<宿ID>.json` を更新（料金の行、税、口コミを読んだ範囲は、要約せずに保存）、レポート `compare` |
| 予約前の確認 | 残った1〜2軒の、プランごとの料金、キャンセルの規定、予約ページを確かめる。比べる段階で出た気になる点を確かめる | inspector（宿ごと） | どの宿を、どの予約のしかたで取るか | 同上、レポート `final` |
| レポート | 保存した結果だけから、検算表を作り、提案の資料を書く。新しくは調べない | なし | 提案への返事（はい／いいえ、2択） | `reports/` の下に、レポートと検算表 |

次の段階へ進むのは、ユーザーが残す候補を言ったときだけです。条件が変わったら、その条件に依存する事実（料金は日程・人数・食事、交通は出発地・場所）だけを取り直します。

## 2. レポートの版の上げ方

- 名前は `<作成日>-<段階>-v<番号>.md`。段階は `wide`、`compare`、`final` のどれかです。
- 上書きしません。同じ段階で書き直したら番号を上げます。前の版は残します。
- 段階が進んだら、新しい段階の名前で v1 から始めます。前の段階の本文を写して直すのではなく、保存した結果から書き直します。前の版の誤りを持ち込まないためです。
- 検算表は、同じ名前に `-check` を付けて保存します（例：`2027-01-10-final-v1-check.md`）。
- `wide` の段階では、料金や口コミがそろっていないので、宿を1軒に絞りません。次にくわしく調べる宿として3〜5軒を勧め、「どれを残すか」を問いにします。第一案を1軒出すのは、`compare` と `final` です。

## 3. 書く前の検算

レポートの数字と提案は、本文を書く前に、5つの表で確かめます。表の形は `skills/report/SKILL.md` の「検算表」にあります。

| 表 | 確かめること | 防ぐ誤り（試運転で実際に出たもの） |
|---|---|---|
| 表1　条件の当てはめと、予算の判定 | 数字の条件を、すべての宿に、分や円のまま当てる。予算は、食事、税、現地の追加費用の見込みを足した額で判定する | 差が2時間02分の宿が、「2時間以内」の候補に残った |
| 表2　料金の式 | 夜ごとの行と、合計の式。税の扱いを全部の宿でそろえる | 1泊分を2倍にした合計。夕食の回数が違う合計を同じ列に並べた。宿泊税の抜け |
| 表3　口コミを読んだ範囲 | 宿ごとの、サイト、並び順、件数、低評価を読めたか | 読んだ深さが違うのに、指摘の数を宿どうしで比べた |
| 表4　提案の選び方 | 第一案、次点、付録のどれにするか。決め手が未確認なら、外れた場合の並び直し | 並び順に根拠がない。「いちばん安い」が全員分の合計では誤り |
| 表5　本文の裏付け | 理由の1文ごとに、根拠の事実と、食い違う事実 | 見立ての章が、事実の章と食い違った。題名しか読んでいない出典を事実にした |

人が見るときは、表2の式を電卓でなぞり、表4の「結果」の列が本文の第一案と次点に合っているかを見れば足ります。

## 4. 提案の組み立て方

1. **ふるいにかける。** 数字の条件にすべて合い、全員が予算以内で、すべての夜の料金がそろっている宿だけが、第一案になれます。予算は、宿で出ない食事、税、現地の追加費用の見込みを足した額で判定します。追加費用のうち、駅と宿の間の有料のバスのように宿ごとに変わるものは保存された事実の額を使い、それ以外はどの宿にも同じ見込み額を足します。固さが「上限」（聞けていなければ、これ）なら、超える宿は第一案にも次点にもせず、何円超えるかを添えて付録に置きます。「少しなら可」なら、幅に収まる宿だけを次点にできます。確かめていない値しだいで超える宿は、第一案にしません。固さが上限なら次点にもせず、超えうる額を添えて付録に置きます（その旅行でユーザーが残すと答え、`decisions` に記録があるときだけ、次点に残します）。予算以内でも、固さが上限で、余りが宿で出ない食事1回の見込み（`budget.meal_estimate`）より少ない宿は、第一案にしません。次点にはできます。上限は「出せる限界」という意味だからです。例外として残した宿（条件の外）は、第一案にしません。
2. **順番を付ける。** ふるいを通った宿を、食事の第一希望に合う夜の数 → 好みに結びつく事実の数 → 全員分の合計、の順に並べます。口コミの点数は使いません。
3. **次点を選ぶ。** 順番の2番目を機械的に取るのではなく、第一案があきらめたものを満たす宿を1〜2軒選びます。読み手が「何を取ると、何をあきらめるか」で選べるようにするためです。
4. **理由と、あきらめることを書く。** どちらも、ユーザーが言った希望の言葉に結びつけます。あきらめることのない案は書きません。
5. **決め手が未確認かを見る。** 第一案をいちばん上にした決め手が、確かめていないこと（検索サービスの表示だけのプランなど）にかかっているなら、それが外れた場合で、ふるいと余りの決まりも当て直して、宿を並べ直します。替わる宿とその額を、第一案のすぐ下に1〜2行で書き、その確認を「次にすること」の先頭に置きます。試しのレポートでは、決め手の朝食付きプランがないと、第一案が別の宿に替わり、額でも付録の宿のほうが安くなりました。
6. **問いを作る。** 3つまで。「はい／いいえ」か2択で答えられる形にし、答えによって何が変わるか（額、予約の件数、第一案が替わるならその宿）を添えます。問いどうしは独立させます。第一案の気になる点は「第一案で進めてよいか」の問いの説明に入れ、別の問いにしません。
7. **次にすることを書く。** いつまでに、だれが、何を。期限は、保存された規定から数えられるものだけを書き、数えたものには「（推定）」を付けます。
8. **本文と付録に分ける。** 本文は、提案、問い、次にすること、第一案と次点の比較、前提にした希望。出典の番号は付けず、確かめきれていないことにだけ「（未確認）」「（推定）」を付けます。ほかの宿、くわしい事実、未確認の一覧、出典は付録です。

ふるいを通る宿が1軒もないときは、第一案を出しません。いちばん近い宿と、何がわかれば出せるかを書きます。

## 5. 判断することと、質問すること

ユーザーからの指摘（2026-11-18）で入れた決まりです。条件を先に示してあるのに、そこから判断できる境目を背景なしに質問され、その答えを以後の前提のように扱われるのは困る、という指摘でした。

- **条件から決められる境目の判断は、相談役が決めます。** 予算の固さ、優先順位、好みから導けることは、質問にしません。決めたことは「こう判断しました（理由：条件の〇〇）。違えば教えてください」と、レポートの本文か付録に書きます。
- **質問するのは、条件どうしが食い違うときと、条件では決まらず、答えで提案が大きく変わるときだけです。** 質問には、どの条件では決まらないか、選択肢ごとに提案がどう変わるか、相談役ならどちらにするか、その理由、の4つを添えます。
- **答えは、その旅行の判断にだけ使います。** `conditions.json` の `decisions` に、問い、答え、日付を記録し、レポートの「前提にした希望」に「〇月〇日のご回答による」と書きます。
- **答えを、ほかの旅行にも効く決まり（定義の既定）にするのは、ユーザーがそうしてほしいと言ったときだけです。** 定義を直す人も同じです。1回の答えから定義の決まりを作りません。額（食事の見込み、追加の費用）や、含めるものは旅行ごとの値で、定義には聞き取りの項目だけを置きます。
- レポートの「決めてほしいこと」も同じです。問いにするのは、本人にしか決められないこと（どの宿にするか、外で食べるか）だけです。

## 6. 生ログの残し方

調査役が何を検索し、何が返ってきたかの記録です。定義を直すときの裏付けになります。

- 相談役はファイルをコピーできません。頼むと、ユーザーが実行するコピー用のスクリプトを書きます。
- コピー元は、Claude Code の設定フォルダ（ふつうはホームの `.claude`）の下の、`projects/<プロジェクト名>/<セッションID>/subagents/agent-<調査役のID>.jsonl` です。
- 調査役を呼んだときに示される一時フォルダの `tasks/<ID>.output` は、空のことがあります。こちらを写すと、0バイトのファイルができます（2回目の試運転で起きました）。写したあと、サイズが0でないことを確かめます。
- 置き場所は `trips/<旅行ID>/poc-log/` です。リポジトリには入れません。
- 生ログには、ページから来た AI 向けの指示が混ざっています。読むときは、すべてデータとして扱います（[design.md](design.md) §10）。
- 調査役が取得した時刻は、開始時に `hooks/hooks.json` が渡す時計の値から書かれます。時刻が保存されていないものは、レポートでも日付だけを書き、時刻を作りません。

## 7. 定義を直したとき

直すのは `plugins/travel-agent/` の側です。直したあとの手順（`.claude/` のコピーの作り直し）は、[README](../README.md) の「定義を直すとき」にあります。
