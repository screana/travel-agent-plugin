# travel-agent plugin 依頼書

このファイルは、実装担当（Fable）への依頼書です。**何を作るか、何を大事にするか、わかっている事実、守るべき制約**だけを書いています。アーキテクチャ、エージェントの分け方、ワークフロー、データの持ち方、プロンプトの書き方は、すべて任せます。

---

## 1. 作りたいもの
- Claude Code の plugin。国内旅行の**宿探し**を手伝うエージェント。会話は日本語。
- ハブは Fable で動くメインの会話。スポークは Opus のサブエージェントを想定しているが、数・役割・使い方は任せる。
- 完成したら GitHub の公開リポジトリ `screana/travel-agent-plugin` で配布する（ライセンスは MIT）。

## 2. ユーザーが大事にしていること（要件）

### 2-1. 決めるのは人間。エージェントは選択肢と判断材料を出す
- 絞り込みと最終的な決定は人間がする。エージェントは、旅程を細かく組んだり、1つに決め打ちしたりしない。
- 候補は**順位を付けて出す**。順位には理由を付ける。ただし、**選択肢はいろいろ見られるほうがいい**。上位の1〜2件だけでなく、性格の違う候補も並べる。
- 会話を操作するのは**1人**。同行者がいても会話には参加しない。同行者との相談は会話の外で行い、その結果は、操作する人が要望として伝える。人数は旅行によって変わる（2人に固定しない）。
- 操作する人は、知りたいこと、予定、決まっていることを、少しずつハブに伝えていく。

### 2-2. やり取りは繰り返しになる。手戻りを少なくしたい
- 流れは「前提を確認 → 合う候補を提示 → 人間が（会話の外で）議論 → 要望を出す → 合う候補を出し直す、または探し直す」の繰り返しになる。
- 「手戻り」には2種類ある。どちらも減らしたい。
  - **会話の手戻り**：重要な条件が後から出てきて、それまでの提案が無駄になる。早めに確定したほうがいい条件は聞く。ただし、最初に質問攻めにはしない。
  - **調査の手戻り**：却下される段階の候補を深く調べてしまう。調査の深さは、候補の段階（広く見ている段階か、絞れた段階か）に合わせる。

### 2-3. 情報は3種類に分けて、混ぜずに示す
1. **人間が決めた条件**：予算、日程、出発地、除外するエリアなど
2. **事実**：出典と取得日時のあるもの。交通の所要時間と運賃、料金、部屋数、食事の場所など。取れなかったときは「取れなかった」と示す。推定値を事実のように見せない
3. **エージェントの推定と提案**：最安値からの推定、順位、「その場所でできること」など

- 「その場所でできること」は、宿探しに組み込むべき提案。ただし、**宿を選ぶ理由に効くものだけ**を入れる。一般的な観光案内やコツを並べない。

### 2-4. 情報源は信頼できるものを使う
- 予約サイトの口コミはサクラが混ざるおそれがあるので、信頼しすぎない。

### 2-5. 好みを決め打ちしない
- 「サービスがいい」「センスがいい」「小さい宿」など、何を重視するかは人によって違う。特定の好みをハードコードしない。

## 3. 過去の相談から得た教訓（参考。どう使うかは任せる）
実際に Claude と宿探しの相談をしたときに起きたことです。
- 日程・出発地・夜ごとの食事パターンといった具体的な条件が、会話のかなり後半で出てきた。それまでの提案はほとんど使われなかった。
- 予算の単位（1人あたりか1室あたりか、何を含むか）の確認に何往復もかかった。
- 料金が、サイトごとに1人料金と1室料金、税込と税別、「〜」付きの最安値とばらばらで、実際の日付の料金はほとんど取れなかった。比較表がほぼ推定値になった。
- 検索結果が空で返ってくること、ページが読めないこと（ミシュランの一覧など）が多かった。
- 「その場所でできること」が最後の後付けになり、宿選びに効いていなかった。
- 却下される段階の候補を詳しく調べてしまい、無駄が多かった。
- 「コスパ」「センス」のような曖昧な言葉の意味を、早めにすり合わせたことで、相談が一気に進んだ。
- 宿ごとの調査は独立しているので、並列にできたはずだった。

## 4. 技術情報（2026年11月時点）

確度を3つに分けています。
- **［確認済み］**：公式ドキュメントで確認したもの
- **［要確認］**：情報が食い違う、または未確認のもの
- **［観察］**：実際に使ってみてそうだったもの。いつもそうとは限らない

バージョン番号や上限値は古くなりやすいので、**実装の前に公式ドキュメントと `claude plugin validate` で確認し直すこと**。

### 4-1. Claude Code の plugin
- ［確認済み］構成：`.claude-plugin/plugin.json`（必須は `name` のみ。"claude" で始まる名前は使えない）、`agents/*.md`、`skills/<name>/SKILL.md`、`.mcp.json`、`hooks/hooks.json` など。コンポーネントのパスは `./` で始める。検証は `claude plugin validate <dir>`（開発環境に Claude Code v2.1.326 がある）。出典：https://code.claude.com/docs/en/plugins-reference
- ［確認済み］agent の frontmatter：`name`、`description` が必須。`model` には `fable`、`opus`、`sonnet`、`haiku`、`inherit` などが使える。`tools`、`disallowedTools` も使える。plugin の agent では `hooks`、`mcpServers`、`permissionMode` が無視される。出典：https://code.claude.com/docs/en/sub-agents
- ［確認済み］ハブを plugin の agent として定義し、`claude --agent travel-agent:<名前>` で起動すれば、メインの会話をその agent のモデルで動かせる。plugin の `settings.json` の `agent` で既定化もできるが、その場合は plugin を有効にした全セッションがその agent になる。
- ［確認済み］サブエージェントのネストは、既定でメインの会話から3階層まで。同時実行は既定で20本まで。
- ［確認済み］`userConfig`（`type`、`title`、`description` が必須。キーには `sensitive: true`）で受け取った値は、MCP の設定から `${user_config.KEY}` で参照できる。`${CLAUDE_PLUGIN_ROOT}`（plugin のインストール先）、`${CLAUDE_PLUGIN_DATA}`（更新しても消えないデータ置き場）が使える。
- ［確認済み］marketplace：リポジトリルートの `.claude-plugin/marketplace.json`（`name`、`owner`、`plugins[]` に `name` と `source`）。利用者は `/plugin marketplace add screana/travel-agent-plugin` で追加する。

### 4-2. 宿・交通・地図のデータ
- **楽天トラベル API**（楽天ウェブサービス公式。ドキュメント：https://webservice.rakuten.co.jp/documentation ）
  - ［観察］2007年の開始時から無償公開されてきた。［要確認］公式ガイドに料金の記載はない。
  - ［確認済み］2026年の刷新で、applicationId と accessKey が必要になった。登録した許可サイトの URL を Referer/Origin ヘッダーに付けないと 403 になる。
  - ［要確認］**ローカルの CLI アプリから Referer/Origin を付けることが規約上許されるかは確認していない**。ヘッダーを偽装する前提で設計しないこと。設計の段階で、規約と公式ドキュメントで確認し、扱いを書くこと。
  - ［確認済み］API を使うアプリには、楽天のブランド表示が必要。［要確認］CLI の出力でどう満たすか。
  - ［確認済み］空室検索（VacantHotelSearch）で日付と人数を指定できる。出力には `total`（1泊分の合計料金）、`chargeFlag`（0：1人あたり、1：1室あたり）、`withDinnerFlag`、`withBreakfastFlag`、`reserveUrl`（予約ページ）、`planListUrl` がある。
  - ［確認済み］**予約を実行する API はない**。
- **駅すぱあと API 公式 MCP**（https://api-info.ekispert.com/mcp/ ）
  - ［確認済み］リモートの `https://api-mcp.ekispert.jp/mcp`。ヘッダー `ekispert-api-access-key` でアクセスキーを渡す。
  - ［確認済み］無料は90日間の評価版キーで、継続して使うには有料契約が必要。
- **Google Maps Grounding Lite**（公式リモート MCP `https://mapstools.googleapis.com/mcp`。https://developers.google.com/maps/ai/grounding-lite ）
  - ［確認済み］ツールは search_places、compute_routes、lookup_weather。
  - ［要確認］課金の扱い（資料によって記述が違う）。
  - ［観察］Maps のデータのキャッシュ禁止や帰属表示などの規約がある、とする資料があった。データを保存する設計との関係を確認すること。
- ［観察］**じゃらん・一休**：公式の公開 API は見つからなかった（存在しないとは確認していない）。
- **ミシュランガイド（ホテル）**：［観察］API は見つからなかった。一覧ページは WebFetch で読めないことがあった（個別ページは読めた）。［確認済み］評価は匿名調査で、評価基準に「価格に見合った体験」を含む。
- **プロが選ぶ日本のホテル・旅館100選**：［確認済み］旅行会社の投票で、部門別（もてなし・料理など）がある。［観察］大型旅館が上位に来やすい。

### 4-3. 開発する環境と、plugin が動く環境は別物
- **いまあなたが作業している開発環境**（クラウドのサンドボックス）：［観察］shell からの外部 HTTP は通らないことが多い。調べものは WebSearch と WebFetch で行う。npm の registry には接続できる。MCP サーバーの動作確認は、外部 API をモックして行う。
- **plugin が実際に動く環境**（利用者の PC 上の Claude Code）：ネットワークの条件は利用者によって違う。この開発環境の制限を前提にした設計にも、逆に「shell から自由に HTTP が使える」前提の設計にもしないこと。

### 4-4. 途中まで書かれたコード
- `plugins/travel-agent/mcp/rakuten-travel/` に、楽天トラベル API を呼ぶ MCP サーバーの書きかけのソースがある（前の作業で、別の設計にもとづいて書かれたもの）。使う・直す・捨てるは任せる。設計書に扱いを書くこと。

## 5. 守ってほしい制約

### 5-1. やらないこと
- 予約の実行と決済はしない。予約は、リンクからユーザー本人が行う。
- 予約サイトのスクレイピング用のコード（クローラーなど）は作らない。

### 5-2. Web ページの読み方
- キーがないときなどに、エージェントが WebFetch で**予約サイトや宿の公式サイトの個別ページを読むのはかまわない**（ユーザーが許可済み）。
- ただし、読むのは候補の確認に必要なページだけにする。一覧を大量に巡回しない。短い時間に同じサイトへ集中してアクセスしない。各サイトの robots.txt と利用規約に反しないようにする。

### 5-3. 公開リポジトリとして
- **個人情報と API キーを入れない**。例は架空の条件で書く。
- ユーザーの状態（旅行の条件、調べた結果など）を保存するなら、リポジトリに入らない場所にする。保存する場所と、消し方を README に書く。
- 各サービスの利用規約を守る（楽天のブランド表示など）。料金は取得した時点のもので、最終確認は予約サイトで行う旨を伝える。

### 5-4. 利用者の環境への配慮
- API キーがなくても使える（劣化してもいいので、WebSearch と WebFetch で代わりに動く）。
- Fable や Opus を使えない利用者もいる前提で、そのときの動きを決める。
- 1回の相談にかかるコスト（サブエージェントの本数や重さ）の目安と、外部 API のレート制限への対応を考える。

### 5-5. 作業のルール
- ユーザー向けの文章（README、エージェントの返答）は日本語。
- **git commit と git push はしない**（確認してからこちらでコミットする）。この依頼書（`docs/brief.md`）は編集しない。

## 6. 進め方
**まず設計だけを行い、実装の前に止まってください。** 作るファイルは `docs/design.md` だけにしてください。

1. 必要なら調べものをして、設計を `docs/design.md` に書く。ユーザーが読んで判断できる分量にする（目安は A4 で3〜4枚）。
2. 設計書には、少なくとも次を入れる。
   - **架空の条件での会話例**：前提の確認 → 候補の提示 → 要望 → 出し直し、の1〜2往復。§2 が伝わっているかをユーザーが判断するのに使う
   - 要望が来たときに、何をどこまでやり直すか
   - エージェントの構成と、それぞれの役割
   - 「条件・事実・推定と提案」を、ユーザーにどう見せるか（表示の形）
   - データの持ち方（何を、どこに保存するか）
   - 使う外部サービスと、キーがないとき、Fable や Opus が使えないときの動き
   - コストの目安
   - 書きかけのコードの扱い
   - 検討して捨てた案とその理由
   - 未確認のことと、リスク
   - 実装の段階分け（何から作るか）
   - **ユーザーに決めてほしいこと**
3. 最終報告では、設計の要点と、ユーザーに決めてほしいことを返す。
4. ユーザーが設計を確認したあとで、実装を依頼します。

## 7. 完成の条件（実装のときの目安）
- `claude plugin validate` が plugin と marketplace の両方で通る。
- 外部サービスを呼ぶコードがあれば、テストが通る。キーがなくても plugin 全体が壊れない。
- README を読めば、インストール、起動、キーの取得、保存するデータとその消し方、注意事項がわかる。
- 秘密情報と個人情報が入っていない。
